## 1. 一個被當成事實引用的錯誤

`CONTEXT.md` 對**掃單**的定義是:

> 同一檔**相鄰且同毫秒**(TC4 PreciseTime)的一群成交

而 `tc4-market-facts` skill 的「同毫秒群」節明文寫「REALTIME 與歷史 TICKS 的毫秒同源」。

**那句話是錯的。** prod 的 REALTIME 推播在這個欄位上的實際解析度是**秒**,不是毫秒。

後果:
- 線上偵測器**對自己自洽**(它用同秒群,穩定產生事件),但它的事件母體與研究的 1,883 股票日母體**不同源**。
- 而 `+5,784/筆`、`鎖死 23%` 這些影子期要拿來對照的基準,全部是在**毫秒母體**上算出來的。
- 要修的不只是門檻,是**一條被當成事實引用的 skill 條目**。

目前純影子、零下單,所以這是研究有效性問題不是資金風險。但它直接決定四週後那場對帳能不能成立。

## 6. 改造順序

### Step 0 — 影子期急救(今天就該做,每天都在流失)

| # | 動作 | 為什麼急 | 判準 |
|---|---|---|---|
| 0a | **規則 CRUD 加審計**(誰、何時、改了什麼) | 每過一天,那天的事件母體定義就永久不可還原 | 改一次規則 → 審計檔出現帶時戳的前後值 |
| 0b | **門檻寫進政策列**(掃單簇 params + 政策門檻) | 中途調參後對帳分不出前後 | jsonl 新列含門檻快照 |
| 0c | **未命中事件也落族群快照** | 36% 事件現在無法做敏感度分析;修法**幾乎零成本** | jsonl 有未命中列 |
| 0d | **jsonl 加 `boot_id` 斷點記號** | 5 天中 3 天有重啟,重複 8–43 則且認不出來 | 重啟後 jsonl 新列 `boot_id` 改變 |
| 0e | **rule_id 穩定化**(種子規則落檔,不要每次開機重生) | 跨重啟無法配對同一顆事件;而且**任何一次 UI upsert 會把當下的隨機 id 永久凍結** | 重啟兩次,`data/signal_rules.json` 的 id 不變 |
| 0f | **`DISCORD_WEBHOOK_URL` 補上** | 一行 env、零程式,補掉 bot 啟動窗的退路 | `python -m copycat notify-test` 通過 |

**0a–0e 做完之前,四週影子期的後半段才有意義。**

### Step 1 — 決定掃單簇母體(需要你拍板)

prod 是同秒群、研究是同毫秒群。三個選項:

| 選項 | 做法 | 代價 |
|---|---|---|
| A | 承認 prod 是同秒群,**用同秒群重跑研究基準** | 研究要重算,但線上不動 |
| B | 找出 TC4 有沒有真毫秒欄位,線上改成毫秒 | 若沒有就走不通;要先驗 |
| C | 維持現狀,四週後只做**相對比較**(不跟研究絕對值對) | 影子期的價值大打折扣 |

同時要修 `tc4-market-facts` skill 那條錯誤條目。

### Step 2 — 失效模式補洞

`S` 政策母體缺席告警、排除組名零命中告警、live 跨日清空、Discord 節流改成「丟棄要記名單」、桌面通知的 latest-wins 覆蓋。

### Step 3 — 效能去重(S1/S3 那四條)

`_distribute` 補 `enabled` → `evaluate_book` latch 短路 → `_eval_volume` running sum → detector 拆兩層。

**判準**:每 tick 的訊號層成本從 20.7–78.5 µs 降到 ~10 µs;30 條規則的記憶體不再線性成長。

### Step 4 — 延遲記帳

`now − tick.time` 落在訊號列上。這是 §7 開下單的必要前提。
