## 0. 三句話結論

1. **送單方向已經沒有 Python 可優化的空間了。** 端到端 mean 89.6 ms,本地所有 Python 段加起來 **1.14 ms(1.3%)**。剩下 98.7% 在 COM + 券商。
2. **真正慢的是回流方向。** 成交回報 → 部位落地 p50 **1,940 ms**、p99 **6,553 ms**(179 條 prod 實測鏈)。比送單慢 20 倍,這才是「下單後倉位很慢」的來源。
3. **最危險的不是慢,是兩條靜默路徑**:回報斷線偵測是死碼(65 次 session、0 次觸發);前端 TanStack 預設把送單失敗變成「暫停排隊」,網路恢復後**自動補送真錢單**。

### 重要更正(查核推翻了掃描的兩個說法)

- 掃描說「黑箱只有 ⑨ 一格」。**錯** —— ⑧ 的 COM 半邊與 ⑪ 都標未量,而且**兩者都落在審計的兩個時戳之間**。所以 88.5 ms 的殘差是 **⑧(COM 半)+ ⑨ + ⑪** 的合計。
- 掃描說「典型單耗 84 ms」。**不可斷言** —— 審計時戳只有秒解析度,p50 的 Δ = 0,中位數只知道 **< 1 s**。可以斷言的是:**mean 84–89 ms**、**P(≥1 s) ≈ 7.6–7.8%**、觀測最大 3–4 s。

### 兩個對照

- 拒單 mean **173 ms** vs 成功 **81 ms**。
- 與本機負載**不相關**:09:00–09:05 開盤 26 筆零跨秒,11:00–13:30 反而 14.3% 跨秒 → **尾巴在券商端**,不在我們這裡。

### 這張表的結論

**不要優化送單路徑的 Python。** 把 ①–⑬ 全部優化到零,端到端只從 89.6 ms 變成 88.5 ms。

唯一有意義的槓桿是 **⑨ 的 `bAsyncOrder=0`**:同步呼叫期間唯一那條 COM 執行緒完全不能 pump 回報、不能發回查、不能取下一個命令(head-of-line blocking,**機制已 CONFIRMED**)。改非同步不會讓單更快送到券商,但會讓**那 7.6% 的長尾不再卡住回報處理**。

179 條 prod 完整鏈實測(`grep 'balance 鏈' logs/*.log`,程式已內建毫秒計時)。

| 分段 | p50 |
|---|---|

- **「緊急停止要 83 秒」不成立**:健康路徑 1–3 s,硬殺立即。真正的代價是**沒有比殺 process 更細的粒度** —— 殺掉會連帶失去部位快照、回報連線、TC4 五條 session,那才是不敢按的原因。

## 5. 改造順序

### Step 0 — 三件零風險的前置

| # | 動作 | 判準 |
|---|---|---|
| 0a | `QueryClient` 加 `mutations: { networkMode: "always" }` | 斷網後按送單 → 應立即失敗,**不得**在恢復後自動補送。一行改動 |
| 0b | 審計時戳改毫秒 + 加 `request_id` | `data/audit/` 新行有毫秒;既有讀者(月復盤)不破 |
| 0c | 分段時戳 `perf_counter_ns`(②③⑤⑦⑨⑩⑫) | 審計行帶 `lat_us` 各段;端到端 p50 **第一次真的量得出來**(現在只能說「92.4% < 1 s」) |

**0c 是後面每一步的前提。** 現有 499 對配對受限於秒解析度,p50 永遠量不出來。

### Step 1 — 讓警報能響

| # | 動作 | 判準 |
|---|---|---|
| 1a | 修 `OnConnect` / `OnDisconnect` 綁定(C1) | 手動拔網 → log 出現斷線行、`/api/health` 的 capital 格翻 `degraded` |
| 1b | `/api/health` 加 capital 區塊(連線狀態、`_cmd_q` 深度、在途命令數、最後回報時刻) | `curl /api/health` 看得到這五格 |
| 1c | 下單鏈接上 Discord 告警(拒單、逾時、結果未知、斷線) | 觸發一次測試拒單 → Discord 收到 |
| 1d | 前端讀 `err_msg` 與 `OrderResult.ok === false` | 六種拒單顯示不同文案;「結果未知」跳明確警告而不是靜默 200 |

**注意**:1a 單獨做的可見收益比想像小 —— `_execute_write`(`client.py:881-883`)對 `degraded` 是**刻意放行**,而主要下單介面 `PriceLadder` 根本不讀 status。**1a + 1d 要一起做**才有 blast radius。

### Step 2 — 資源隔離(便宜的結構性保險)

具名 audit ThreadPoolExecutor,與 TC4 取數分池。

- **判準**:用 20 條假 worker 塞滿預設 executor,送單前置審計仍應 < 1 ms 完成。
- **隱藏代價**:`ThreadPoolExecutor` 的 worker 是 **non-daemon**,直譯器退出時會 join 全部;`shutdown(wait=False, cancel_futures=True)` 只丟得掉還沒開跑的。要同步檢查 `shutdown_budget` 的不等式(CLAUDE.md §4 三方同源契約)。
- **`fsync` 的取捨**:p50 只多 70 µs,但 **p99 從 353 → 491 µs(尾巴變差)**。審計是「錢動了不可重建」的檔案,我建議做,但驗收判準要看 p99 不是 p50。

### Step 3 — 逾時命令 TTL + 佇列上界

- **判準**:注入一個 15 秒卡住的假 COM 呼叫,逾時的命令**不得**在恢復後送出;`_cmd_q` 超過上界時明確拒絕而非無聲堆積。

### Step 4 — 回流鏈提速(最大的單一改造標的)

成交 → 庫存 → 損益 → OI 三段串行 p50 1,940 ms。

可能的方向(需先用 Step 0c 的分段時戳確認):
- 0.5 s debounce 是否可縮短或改成「首筆立即 + 後續合批」
- 三段能否並行(庫存與 OI 不互相依賴?)
- 六類不樂觀套用的情況能否縮小

- **判準**:`grep 'balance 鏈' logs/` 的 p50 從 1,940 ms 下降;部位面板在成交後多久追上(人可感知的驗收)。

### Step 5 — `bAsyncOrder=1`(L)

前置條件:「等命令」與「等 COM 訊息」現在是兩個互斥的等待,要先重構成單一等待迴圈。

- **收益不是延遲,是消除 head-of-line blocking** —— 那 7.6% 的 ≥1 s 長尾期間,回報不再被卡住。
- **判準**:注入一筆慢單,期間回報仍持續處理(log 有 `OnNewData` 交錯)。
- **風險**:非同步回報的配對邏輯是新 code,而且**第一次執行必然在盤中真錢**。建議先在盤後用最小金額實單驗一次。

### Step 6 — 風控補齊(自動化下單的 blocker)

現況是人工下單(一天個位數)+ `CAPITAL_ORDER_ENABLED` 總開關,裸奔風險有限。**接訊號自動下單前必須先有**:

1. **runtime kill switch**(比殺 process 細的粒度 —— 現在只能殺 process,連帶失去部位快照與 TC4 五條 session)
2. 送出前去重窗(冪等,做在我們這側)
3. 帳戶級累計曝險 + 當日損益加總 + 自動熔斷(**輸入資料全部現成**,缺的是加總與閘)
4. 送單頻率上限
5. 異常行情擋單(鎖漲跌停、**緩撮**、**試撮**窗)

## 6. 不要動

| 項目 | 理由 |
|---|---|
| `capital/safety.py` 全檔 | 五個純函式閘合計 < 5 µs。它是**安全邊界不是熱路徑**,任何「優化」都是在動拒單判準 |
| `capital/mapping.py` 四層收斂 | 實測含 stat 也只有 ~50 µs。第 4 層結構判別是為「個股期上線後整條被送進期權面」那個 P0 設計的,動它就是動送單分流 |
| `stkfut_map.py::_product_index` 的 `stat()` 簽章 cache | 實測 0.004 ms。拿掉 = 新上市個股期被拒單而對映檔明明已更新 |
| COM 執行緒模型(20 Hz 幫浦 / `_cmd_q` + future / `shield` 保護真錢命令) | COM STA 讓它沒有別的寫法,且目前完全不是效能瓶頸 |
| `shield` + 「結果未知,勿重送」+ late 補審計 | 真錢路徑上最難寫對的一段,**已經寫對了** |
| 送單路徑的任何 Python 微優化 | 全部加起來只有 1.14 ms / 89.6 ms |

**另外**:`_cmd_q.get(timeout=0.05)` 的 50 ms **不是輪詢週期** —— `queue.Queue.get` 阻塞在 Condition,`put()` 會 notify 立刻喚醒(實測取件 p50 46 µs)。上界是 `_pump_once()` 的最大耗時,不是 50 ms。不要為了這個「50 ms」去改它。

## 7. 待拍板

1. **回流鏈(Step 4)要不要排在 Step 1 之前?** 它是使用者唯一感知得到的慢,但風險比裝儀表高。
2. **`bAsyncOrder=1`(Step 5)要不要做?** 收益是消除 head-of-line blocking,代價是新 code 第一次執行必然在盤中真錢。
3. **`OnOpenInterest` 欄序**要不要在有期貨部位之前先驗?現在是猜的,而它掛在真錢平倉路徑上。
4. **U / P / B / S 四條狀態轉移**要不要在盤後用最小單實測一次?現在 prod 零執行。
5. 自動化下單的時程 —— 這決定 Step 6 的優先序。
