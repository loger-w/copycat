## 1. 最重的一條:同毫秒 vs 同秒,到底是 (a)(b)(c) 哪一種

### 1.1 現象確認(我自己數的)

`data/signals/*.jsonl` 26 個交易日全量,由 `id` 尾段還原 `time_key` 的毫秒位:

```
cdp_cross      .000=3994  非零=0
crash          .000= 658  非零=0
limit_lock     .000= 176  非零=0
policy         .000= 151  非零=0
surge          .000= 963  非零=0
surge_pullback .000=1225  非零=0

vol_burst      .000= 480  非零=0
limit_open     .000=  22  非零=69     ← 唯一有非零毫秒的 kind
```

tick 路 7,852 列 **100% `.000`**,零例外。報告 §1 的現象描述 **CONFIRMED**。

### 1.2 三選一的決定性證據

**(b)「送了但解析時被截掉」—— REFUTED。**
`copycat/live/stock_models.py:89-95`:

```python
def _taipei_time(precise_utc: str, date_utc: str) -> tuple[str, str]:
    s = precise_utc.zfill(12)
    hh, mm, ss, frac = int(s[:2]), int(s[2:4]), int(s[4:6]), s[6:9]
    ...
    return f"{local:%H:%M:%S}.{frac}", f"{local:%Y-%m-%d}"
```

解析層**真的取三位毫秒並輸出**。而且同一條管線證明得出來它端到端搬得動非零毫秒:
`limit_open` 的 69 列(走 `_clock_key(now)`,`now.microsecond // 1000`)毫秒是非零的,
而它們與 tick 路走**同一個** `time_key` 欄、同一個 `_event_id`、同一個 jsonl writer。

**(c)「送了也解析了但分群邏輯沒用到」—— REFUTED。**
`copycat/live/signal_state.py:729-733` 的開新群判準是 `group.time_key != key`,
而 `key = tick.time or _clock_key(now)`(`:307`)—— 用的是**完整含 `.fff` 的字串**;
窗判定 `tick_secs(key)`(`:167-176`)是 `int(hh)*3600 + int(mm)*60 + float(rest)`,
**float 秒,毫秒進得去**。邏輯完全吃得下毫秒。

**(a)「TC4 REALTIME 根本沒送毫秒」—— CONFIRMED(剩一個 layout 變體待 probe)。**

反證法:假設 REALTIME 的 `PreciseTime` 不是 12 位 `HHMMSSffffff` 而是別的寬度,
`zfill(12)` 會把 HH/MM/SS 整個錯位,時刻就不會是 09:00–13:30 —— 而實測最早桶 `09:00`、
最晚 tick 路桶 `13:30`,全部正確。例如若 REALTIME 送 6 位 `HHMMSS`(= `FilledTime` 那種),
`"10006"` → `zfill(12)="000000010006"` → 恆為台北 `08:00:00.0xx`;實測不是。

正面對照:**歷史 TICKS 的同一欄有真微秒**,repo 內有逐字實錄
(`docs/research/2026-07-06-tc4-stock-tick-1k-api-report.md:57`):

```json
{"Date": "20260703", "FilledTime": "10006", ..., "PreciseTime": "10006840000", "QryIndex": "1"}
```

`zfill(12) = "010006840000"` = 01:00:06.**840**000 UTC。所以**歷史路有毫秒、即時路沒有**,
這是 TC4 兩條通道的差異,不是 copycat 的 bug。

> **唯一還沒排除的變體**:若 TC4 REALTIME 把毫秒放在 `s[9:12]`(而 `s[6:9]` 補零),
> 那就變成 (c) 的 layout 版。這要**一次 raw dump** 才能排除 —— 而 `tc4-market-facts` skill
> 已經記了安全做法(「只聽不訂 probe 寫法」:LOGIN → SUB SubPort、topic `""` → 讀 PUB →
> LOGOUT → Disconnect,零 refcount 影響,盤中安全)。**報告 Step 1 選項 B 寫「要先驗」卻
> 沒有指出這個 5 分鐘就能做完的既有配方。**

### 1.3 skill 那條的精確錯法

`.claude/skills/tc4-market-facts/SKILL.md:71-72` 原文:

> **同毫秒群 = 掃單:個股同一檔相鄰且 `PreciseTime` 毫秒相同的多筆成交** …
> REALTIME 與歷史 TICKS 的毫秒同源(`PreciseTime` 12 位取前 9 位 = `StockTick.time` 的 `.fff`,
> 研究 `pull_ticks.py` 用 `us // 1000` 同一刀)

**錯的是「同源」這個推論,不是括號裡那一刀。** 那一刀(12 位取前 9 位)兩邊確實是同一個式子;
錯在由「同一個式子」推出「同一個群」—— 即時路的輸入在那三位上恆為 0,所以同式不同群。
報告寫「那句話是錯的」方向正確,但**修 skill 時要改的是那半句,不是整條**,否則會把
「12 位取前 9 位」這個仍然正確的解析事實一起刪掉。

## 10. 報告漏掉、但以「高效能量化系統」為目標必須知道的

1. **本機時鐘零紀律,而且已經改變過 gate 結果。** 我獨立驗:`Get-Service W32Time` → `Stopped` /
   `Manual`。實測 09-11 有 **4 則 `vol_burst` 的 tick 時刻 = `13:30:00`**,而 `_in_session`
   右界是 13:30 **end-exclusive** 且用**本機鐘** —— 交易所時刻 13:30:00 的 tick 能穿過,
   代表評估當下本機鐘 < 13:30:00,即**本機鐘落後**。
   **報告的 §3 失效模式表整條沒收這一項**,§2 延遲表也沒提。對一個要下實單的系統,
   「所有 cooldown / 窗 / 盤中閘用的鐘沒校過」比表上任何一條都基本。
   (佐證:同時段 13:25 / 13:26 / 13:29 的列全是 `limit_open` / `market_limit_*` 這些走**伺服器鐘**
   的 kind,只有 13:30:00 那 4 則是 tick 路 —— 兩把尺的分裂看得一清二楚。)

2. **回填 log 的「共回填 0 列」與「健康的無事可做」同字串。** 我在
   `logs/server-20260911-0905.log` 實際看到 09-12 / 09-13 各一行「共回填 0 列(掃 5 個日檔…)」。
   這次是正常的(週末 + hub 日別未前進),但**同一行字也會在「日檔已滑出 5 日視窗、永遠補不到」
   時出現**。這是 Step 0 等級的一行修改(收尾多印「掃描範圍外仍 null:n 列」),
   報告 §3 / Step 0 都沒收。

3. **有第四條路可以直接量掉 Step 1 的爭議,而且不用碰 prod。** 歷史 TICKS **有真微秒**
   (已實證)。把影子期那 5 天的個股歷史 TICKS 拉下來、餵同一顆 `SignalDetector`,
   毫秒版 vs 截秒版的事件集合差異就是**在影子期母體上**的直接量測 —— 不必像 S8 那樣

   三條都比這條貴。

4. **`load_rules` 不回寫檔案 = 影子期有一個沒人講的回退窗。** 只要**沒有人在 UI 按過儲存**,
   `data/signal_rules.json` 就一直是 v1 四條,整個遷移鏈每次開機重跑。
   好處是「規則集完全由 code 決定、可還原」(§7);**壞處是改 `default_rules` / 遷移鏈的任何
   一次 commit,都會在下次重啟靜默換掉 prod 規則集**,而 jsonl 上分不出來。
